Canonical Tag: A Hint Google Can Overrule

Last verified: October 2026 · About 8 minutes of reading

The tag is one line in the head, and it is routinely asked to do more than it can. This guide covers what it actually asks for, the combinations that cancel it, and how to see which URL Google chose instead of assuming.

What a canonical tag does

It names the URL you want treated as the authoritative copy when several URLs serve the same or similar content.

Search engines group near-duplicate pages and pick one representative. The canonical tag is your nomination for that representative. It does not merge pages, delete the others, or transfer ranking by itself; it is one input into a decision the search engine makes.

<link rel="canonical" href="https://example.com/pricing">

The target should be an absolute URL, should return 200, and should be indexable. A canonical that points at a redirect, an error, or a page carrying noindex is a request that cannot be granted.

A hint, not a directive

Google can ignore the tag and pick another URL, so the declared canonical and the selected one can differ.

Google's own wording is that indicating a canonical preference is a hint, not a rule. It weighs several signals: HTTPS over HTTP, redirects, the annotation itself and sitemap inclusion. A redirect is the clearest statement because it removes the duplicate from view. The tag leaves both URLs live and asks Google to choose. When your links, sitemap or redirects point somewhere else, Google may side with them.

Signals Google documents, and how much they settle the question.
SignalStrengthWhy
301 or 308 redirectStrongThe duplicate URL no longer serves the content
rel="canonical"StrongAn explicit declaration, still overridable
Sitemap inclusionWeakSays a URL exists, not which copy is primary
HTTPSPreferredGoogle favours the secure version of a URL

Self-referencing canonicals

A page that names itself is the safest default and prevents parameter variants from competing with it.

The tag is most useful on the clean URL, pointing at itself. That sounds redundant, and it is the point: it states which form is correct when the same content is reachable with tracking parameters, a trailing slash, a different case, or a session ID. Without it, every variant is an equally plausible representative.

Self-referencing does not make a page canonical in Google's index. It only removes ambiguity about which URL the page itself considers correct. If the page is genuinely a duplicate of another, the tag should point at that other page instead, and the two pages should not both claim to be primary.

When canonical and noindex disagree

noindex decides whether the URL is indexed; the canonical's request to consolidate signals into another URL cannot be relied on.

These are opposite instructions on one URL: one says "do not index me", the other says "treat my signals as belonging to that page". Google's guidance is unambiguous about the combination: do not use a noindex tag on pages that carry a canonical pointing elsewhere, because the pages are no longer equivalent with respect to indexing. In practice the URL drops out of the index, and the consolidation you wanted does not happen.

The exception is a self-referencing canonical next to noindex. Nothing is being consolidated anywhere else, so there is no contradiction; noindex simply decides the outcome. If the goal is removal, use noindex alone. If the goal is consolidation, use the canonical alone. If the old URL should disappear entirely, a 301 is stronger than either.

Cross-domain canonicals

A canonical may point at another domain, and Google treats it as the same hint rather than a guarantee.

Google has supported cross-domain canonicals since 2009, which makes them useful when the same content is legitimately published on two domains you control and a redirect is impossible. The pages should be near-identical. Pointing every page of an old site at a new homepage is not a migration strategy; the mapping has to be one URL to one URL.

For syndicated copies you do not control, the hint is weaker still, because the partner page usually differs in template and context. Treat a cross-domain canonical as a request that may be declined, and do not use it as a substitute for a redirect you could actually serve.

When a redirect beats a canonical

Use a 301 when the old URL should disappear; use a canonical when both URLs must keep working.

A redirect changes which URL is served, so there is no duplicate left to consolidate — that is why it is stronger for migrations and retired pages. A canonical leaves both URLs live and only asks Google to merge their signals, which is the right tool for filtered listings, parameter variants and syndication. A canonical pointing at a URL that returns 404 cannot be honoured: there is no live page to consolidate into, and Google will pick another candidate.

Five mistakes worth checking

Most failures are self-inflicted: the wrong target, a chain, a dead target, a relative URL, or a site that contradicts the tag.

The first row is the expensive one. A canonical is not a way to deprecate a page whose content you no longer want; if the content differs, the tag is simply wrong, and Google is likely to ignore it while the page loses its own standing.

How to check yours

Compare the declared canonical with the one Google selected, then look for the signal that disagrees.

  1. Read the raw HTML. View source, not the inspector, and search for rel="canonical". Confirm there is exactly one and that the href is absolute.
  2. Run URL Inspection. Search Console shows the user-declared canonical and the Google-selected canonical as separate fields. A mismatch is the answer to "why is the wrong URL indexed".
  3. Read the page status. The Pages report distinguishes "Alternate page with proper canonical tag" (working) from "Duplicate, Google chose different canonical than user" (your declaration was rejected).
  4. Check the rest of the signals. If internal links and the sitemap still point at the variant, fix those before rewriting the tag. The free AI readability check reports whether the canonical resolves to the page on the same host and protocol, next to noindex and robots.txt.

What a correct canonical cannot prove: that Google accepted it. The tag cannot make two different pages duplicates, cannot force an index, and cannot repair conflicting links or a sitemap that names another URL.

Frequently asked questions

Four questions cover the strength of the hint, self-reference, cross-domain use and the noindex conflict.

Is rel=canonical a directive?

No. Google calls it a hint and says it may choose a different canonical for reasons of its own. Redirects and the tag are both strong signals, and sitemap inclusion is weaker. When they disagree, Google decides.

Should every page have a self-referencing canonical?

It is the safest default. A page that names itself cannot accidentally nominate a different page, and the tag removes ambiguity for parameter and hostname variants that resolve to the same content.

Can a canonical point to another domain?

Yes. Google supports cross-domain canonicals, and treats them as the same hint as any other. The pages should be near-duplicates, and the target must be a real, indexable URL rather than a redirect or an error page.

What wins when canonical and noindex are on the same page?

The URL usually drops out of the index, so the canonical's consolidation rarely happens. Google publishes no fixed precedence for the combination and advises against it, so noindex alone is the safe way to remove a page.
